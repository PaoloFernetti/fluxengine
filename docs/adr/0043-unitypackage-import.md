# 0043. Импорт `.unitypackage` в flux-assetc: gzip/tar и безопасное дерево путей

- Статус: Accepted
- Дата: 2026-11-15
- Затрагивает: tools/flux-assetc
- Supersedes: —

## Контекст

Ассеты для этапа 5 приходят в том числе из магазина Unity в формате
`.unitypackage`. Это gzip-сжатый tar-архив, где каждый ассет лежит в каталоге
с именем GUID и содержит:

| Файл | Смысл |
|---|---|
| `pathname` | исходный путь в проекте Unity (`Assets/...`, у папок — с `/` на конце) |
| `asset` | содержимое ассета (у папок — пустой файл) |
| `asset.meta` | Unity-meta с `guid` и настройками импорта |
| `preview.png` | необязательный превью-рендер |

Импорт нужен до появления собственного контент-пайплайна (5.1–5.3): иначе
каждый пакет распаковывается вручную, а GUID/meta теряются. Требования:

- никакой паники и path traversal: `pathname` — недоверенный ввод;
- сохранение структуры `Assets/...` и meta рядом с ассетом;
- детерминированный обход (сортировка GUID) и понятный отчёт;
- инструмент остаётся build-time, в рантайм движка ничего не попадает.

## Варианты

1. **Своя реализация inflate/tar.** Плюс — ноль зависимостей; минус —
   DEFLATE (dynamic Huffman, back-references) и ustar/PAX — большой объём
   крипто-подобного кода, который придётся сопровождать и фаззить.
2. **Внешний 7-Zip/PowerShell.** Плюс — нет кода; минус — платформенная
   зависимость, невоспроизводимо в CI, небезопасно для недоверенных архивов.
3. **`flate2` + `tar` (выбран).** Зрелые crates.io-крейты (MIT/Apache-2.0,
   `miniz_oxide` — MIT/Apache/Zlib), оба уже разрешены в `deny.toml`.
   Дают потоковое чтение gzip и разбор tar без ручной работы с форматами.

## Решение

- В `workspace.dependencies` добавляются `flate2 = "1"` и `tar = "0.4"`;
  их использует только `tools/flux-assetc` (build-time инструмент, не
  рантайм-крейт). Это осознанное принятие внешних зависимостей по
  триггеру «готовые зависимости».
- Новая подкоманда:
  `flux-assetc unitypackage <archive> --out <dir> [--no-meta] [--overwrite] [--dry-run]`.
- Алгоритм:
  1. gzip/tar распаковываются в уникальный staging-каталог во временной
     директории; принимаются только записи ровно из двух компонентов
     `GUID/файл`, остальные игнорируются;
  2. для каждого GUID читается `pathname`, нормализуются `\` → `/`,
     отвергаются абсолютные пути, `..`, `.`, префиксы дисков и пустые
     компоненты (`UnsafePath`);
  3. путь с `/` на конце считается папкой и создаётся каталогом; иначе
     `asset` копируется в `output/<pathname>`, а `asset.meta` — в
     `<asset>.meta` (по умолчанию; `--no-meta` отключает);
  4. существующий файл пропускается без `--overwrite`; отчёт считает
     ассеты, папки, пропуски и байты; `--dry-run` только печатает пути;
  5. staging удаляется в любом исходе.
- Порядок GUID сортируется, поэтому результат детерминирован при
  одинаковом архиве. `preview.png` не извлекается.

## Следствия

Плюсы:

- Один воспроизводимый шаг импорта вместо ручной распаковки; meta/GUID
  сохраняются, структура `Assets/` не теряется.
- Недоверенный `pathname` не может выйти за пределы `--out` (тест
  `../escape.txt` → `UnsafePath`).
- Ошибки типизированы (`UnityPackageError`), паники нет; битый gzip/tar —
  `Io`.

Минусы и риски:

- Две новые build-time зависимости; они не попадают в рантайм и уже
  покрыты allowlist-ом `deny.toml`.
- Staging дублирует объём архива на диске; для больших пакетов это
  осознанный компромисс против буферизации ассетов в памяти.
- PAX/GNU-расширения tar не разворачиваются в дерево — принимаются только
  простые `GUID/файл`; экзотические архивы дадут пропуски, а не крэш.
- Импорт не конвертирует форматы Unity (`.mat`, `.prefab`) — это задача
  контент-пайплайна 5.1/5.5, не распаковщика.
