# 0028. Служебный proc-macro пакет flux-macros

- Статус: Accepted
- Дата: 2026-11-13
- Затрагивает: flux-macros, flux-ecs, canon.md, Roadmap (WP 1.1, WP 2.6)

## Контекст

`#[derive(Reflect)]` и атрибуты полей (`#[save]`, `#[replicated]`,
`#[reflect(...)]`) — требование этапа 2: SchemaRegistry должен получать схему
компонента при регистрации, без ручного дублирования списка полей. В Rust
атрибутные и derive-макросы возможны только в отдельном пакете с
`proc-macro = true`; обычный lib-крейт их содержать не может.

Канон фиксирует 18 единиц: 16 крейтов движка + 2 инструмента. Возникает вопрос:
как добавить макросы, не размывая канон и не скрывая пакет от CI.

## Варианты

1. **Ручной `Reflect` без derive.** Каждый компонент пишет `impl Component`
   и `schema()` руками.
   Плюс: ноль новых пакетов. Минус: дрейф схем (забытое поле не попадает
   в сейв/сеть), дублирование, ошибки не ловятся компилятором.
2. **Path-зависимость вне `members`.** Пакет существует, но не виден
   `cargo metadata --no-deps`.
   Плюс: приёмка «18 пакетов» формально не меняется. Минус: пакет не
   тестируется workspace-командой, не виден headless-линтеру и кэшу CI —
   скрытая инфраструктура, а не обход.
3. **Честный пакет workspace + именованный перечень в приёмке.**
   Плюс: прозрачность, тесты, линты, кэш. Минус: `members` становится 19,
   числовой критерий приёмки WP 1.1 устаревает.

## Решение

Выбран вариант 3.

- Создаётся `crates/flux-macros` с `proc-macro = true`. Канон формулирует:
  «16 крейтов движка + 2 инструмента + flux-macros — служебный
  proc-macro-пакет (не единица канона: не движок и не инструмент, только
  дерайвы)». Итого workspace members — 19.
- Приёмка WP 1.1 отказывается от числа: `cargo metadata --no-deps` выводит
  ровно именованный перечень канона плюс flux-macros; ни одного лишнего
  пакета. Числовой критерий ломается при каждом легитимном добавлении,
  именованный — самопроверяем.
- Зависимости пакета: `syn`, `quote`, `proc-macro2` (внешние библиотеки,
  триггер 5 ADR-процесса; входят в это же решение, отдельной ADR не требуют).
- Направление зависимостей строго одно: `flux-macros` не зависит ни от одного
  крейта движка. Дерайвы потребляются `flux-ecs`, позже `flux-anim`, `flux-net`;
  циклы невозможны по построению.
- Генерируемый дерайвом код — публичный ABI контента: сигнатура доступа
  к полям через reflection, имена атрибутов и их семантика меняются только
  новым ADR (совместно с ADR-0030 для формата схемы).

## Следствия

Плюсы: схема компонента и код не расходятся; ошибки атрибутов — ошибки
компиляции; один источник правды для сейва, сети, инспектора и undo.

Минусы/риски:

- +1 пакет в сборке и CI (время компиляции syn/quote).
- MSRV пакета не выше workspace MSRV; проверяется CI.
- Дерайв обязан быть «глупым»: только сбор метаданных, без бизнес-логики
  и без обращения к рантайму движка.
- Ошибки использования атрибутов тестируются `trybuild` (compile-fail).

Заделы: `flux-macros` — единственное место proc-macro в проекте; появление
второго macro-пакета требует нового ADR.
