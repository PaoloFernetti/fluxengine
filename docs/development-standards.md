# FluxEngine — Стандарты разработки

Правило: не существует «правильного» стайла — существует зафиксированный.

## 1. Именование

- Крейты: `flux-<область>` (канон — [canon.md](canon.md));
  инструменты — `tools/flux-<имя>`.
- Модули: snake_case, по ответственности (`rhi`, `archetypes`, `mixing`);
  никаких `utils`, `helpers`, `common` — только конкретные имена.
- Типы: PascalCase; trait-ы — существительные-роли (`Renderer`, `ScriptVM`).
- Поля/переменные: snake_case; единицы измерения — в имени (`_ms`, `_bytes`,
  `_nm` для нанометров канона).
- Форматы/константы формата: UPPER_SNAKE (`MAX_FRAMES_IN_FLIGHT`).
- Термины — строго по глоссарию канона; новый термин = запись в глоссарий
  + владелец.

## 2. Структура репозитория

```
crates/        # 16 крейтов движка (канон, см. canon.md)
tools/         # flux-assetc, flux-build
docs/          # документация + SPA + adr/
examples/      # примеры игр (позже)
```

- Внутри крейта: `lib.rs` реэкспортирует модули; приватность по умолчанию,
  `pub` — только контракт.
- Тесты: юнит — рядом (`mod tests`), интеграционные — `tests/`,
  бенчмарки — `benches/`.

## 3. Rust-стиль

- `rustfmt` (дефолт) — форматирование не обсуждается.
- `clippy`: workspace-lints; на lib-крейтах `clippy::unwrap_used = deny`,
  `expect_used = warn` (expect — только с комментарием-инвариантом).
- Ошибки: пер-крейтовые enum через `thiserror`; `anyhow` — только в
  бинарниках; `unwrap()` без контекста запрещён (CI-линт).
- Паника — только нарушение инварианта; ожидаемые отказы — `Result`
  (ADR-0012).
- `debug_assert!` для дорогих проверок; никаких проверок, зависящих
  от wall-clock.
- Публичные API: doc-комментарии обязательны, с примером использования
  для контрактов; `#[must_use]` на Result-возвратах.
- `unsafe`: только с `// SAFETY:`-комментарием и ревью; предпочтение —
  safe-абстракциям.

## 4. Коммиты

Conventional Commits: `type(scope): summary`.

- type: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`,
  `chore`, `adr`.
- scope — имя крейта/области (`ecs`, `graphics`, `docs`).
- Пример: `feat(ecs): archetype storage with swap-remove`.
- Один коммит — одно логическое изменение; форматтеры — отдельно.

## 5. Ревью (включая соло-режим)

Чек-лист самопроверки до мержа:
- [ ] Триггеры ADR проверены ([adr/README.md](adr/README.md)); при триггере —
      ADR в том же PR
- [ ] Канон/план обновлены, если изменились имена/контракты/форматы
- [ ] Тесты: новый инвариант — новый тест; регресс — regression-кейс
- [ ] Нет `unwrap` в lib, нет `TODO` без issue-ссылки
- [ ] Бенчмарк-гейты не деградировали (для горячих путей)
- [ ] Документация публичного API актуальна

Соло-правило «ревью себе»: PR-описание отвечает на три вопроса — что
изменилось, почему, как проверено. Если ответ «очевидно» — всё равно пишется.

## 6. Документация в коде

- Каждый крейт: `//!`-заголовок с ответственностью и ссылкой на канон.
- Контракты (trait из flux-core/contracts): полный контракт в doc-комментарии
  (кто владеет, кто вызывает, гарантии).
- Сложные инварианты (архетипы, barrier-и, биндлесс-слоты) — doc-комментарий
  с инвариантом, а не «что делает код».
